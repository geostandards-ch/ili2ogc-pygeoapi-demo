# Data provenance

## Model 1: RichtplanungErneuerbareEnergien_V1 (Projection)

### Base model

`models/RichtplanungErneuerbareEnergien_V1.ili` - the real, public federal model
(BFE), fetched from `https://models.geo.admin.ch/BFE/RichtplanungErneuerbareEnergien_V1.ili`.
Vendored here so the demo builds without a network dependency on the model
repository; the derived VIEW model still resolves it via `--repo models`.

### Derived VIEW model

`models/RichtplanungErneuerbareEnergien_V1_d_01.ili` - generated by
`scripts/generate_view_corpus.py --wfs-fixtures` in the `ili2ogc` project
(overlay tooling, not part of the published package), matching the real
`windenergie_flaechen` WFS feature type published by `geodienste.ch`
(`richtplanung_erneuerbare_energien_v1_0_0` theme). `ili2c`-validated.

### Source `.xtf` (not committed)

Real transfer for canton Schaffhausen, downloaded by the `loader` service at
container start:

`https://geodienste.ch/downloads/interlis/richtplanung_erneuerbare_energien/SH/RichtplanungErneuerbareEnergien_V1_SH.xtf`

Contains 3 real `Flaeche` objects. `interlis validate` reports 0 errors (only
expected warnings for `EXTERNAL` catalogue references this single-file
transfer doesn't carry - `Energieform`, `Windenergie`/`Wasserkraft`/etc. -
normal for a standalone cantonal delivery).

### Committed reference artifacts

- `view_flaeche.jsonfg.json` - `interlis convert-jsonfg` output for the
  `view_flaeche` VIEW only (3 Features), the ground truth this demo's
  comparison script checks pygeoapi's own JSON-FG formatter against.
- `view_flaeche.xtf` - the VIEW materialized via `interlis write-xtf
  --merge-with-source`: a self-describing transfer holding the SOURCE
  .xtf's own baskets (the real `Flaeche`/`Punkt`/`Kanton`/... objects)
  PLUS the computed `view_flaeche` VIEW basket appended - one file, no
  separate base file to cross-reference. Round-trips clean through
  `interlis validate` (0 errors).

### Known gap this model worked around (now fixed upstream)

`view_flaeche`'s `ATTRIBUTE` block only projects non-geometry attributes - a
characteristic of a **`PROJECTION OF`** view specifically (this model's WFS
feature-type match had no distinguishing geometry field to map). This is
NOT true of every derived view in `ili2ogc`'s corpus - see model 2 below,
whose `JOIN OF` view maps geometry directly. For a live map-backed demo,
`pygeoapi`'s `flaeche_geo` collection instead serves the **base** `Flaeche`
class (with real geometry, `interlis convert-sql` already splits it
correctly into a normalized `flaeche_geometrie_surfaces` table) - see
`loader/load.py`.

**Fixed upstream**: `interlis convert-jsonfg` did not hoist
`GeometryCHLV95_V1.MultiSurface` (a `STRUCTURE`-wrapped `BAG OF
SurfaceStructure`, not a native `SURFACE`/`COORD`/`POLYLINE` type) to a
JSON-FG top-level `place`/`geometry` member. Not actually a case with no
prior corpus evidence, as first assumed: `ili2ogc`'s own
`docs/jsonfg-conversion-strategy.md` (Lot 5) already hit this exact type
in a real transfer (`wohnungsinventar-zweitwohnungsanteil_2019-10_2056.xtf`'s
`HousingInventory.Geometry`) and used it to deliberately CONFIRM "stays
unsupported" was correct at the time - that lot was scoped to generic
STRUCTURE/BAG/LIST encoding, not to extending `place` hoisting, and the
decision was never revisited until this demo ran into the same case
again. Fixed in `ili2ogc` (`_is_chbase_multisurface` and friends,
`convert/jsonfg.py`) - `Flaeche`'s `place` is now a proper `MultiPolygon`, and
`loader/load.py` reads it directly rather than reaching into
`properties.Geometrie.Surfaces`.

## Model 2: Waldabstandslinien_V1_2 (JOIN OF)

### Base model

`models/Waldabstandslinien_V1_2.ili` - the real, public federal model (BAFU),
fetched from `https://models.geo.admin.ch/BAFU/Waldabstandslinien_V1_2.ili`.

### Derived VIEW model

`models/Waldabstandslinien_V1_2_d.ili` - hand-written for this demo (not
auto-generated - `ili2ogc`'s WFS-driven generator doesn't produce a `JOIN
OF` for this theme yet), following the exact `JOIN OF Waldabstand_Linie,
Typ;` shape already verified end-to-end in the main `ili2ogc` repo
(`docs/verified-view-corpus.md`, Lot 6). `ili2c`-validated; re-verified for
this demo with a real throwaway PostGIS container (`CREATE VIEW` output
identical to `interlis convert-jsonfg`'s in-memory evaluation, field for
field, 5/5 objects).

Unlike model 1's Projection, this `JOIN OF`'s own `ATTRIBUTE` block maps
`Waldabstand_Linie.Geometrie` (a native `LineType`, not a `STRUCTURE`-wrapped
multi-geometry) straight through - `convert-sql`'s `CREATE VIEW` already
carries a real `geometry(LineString, 2056)` column, no base-table geometry
workaround needed. The only workaround still needed:
`view_waldabstand_linie` carries no `id` (a `VIEW` never gets one unless
explicitly mapped) - `loader/post_load_waldabstandslinien.sql` adds a
`waldabstand_geo` convenience view with the base table's own `id` joined
back on, for `pygeoapi`'s `id_field` requirement.

### Source `.xtf` (not committed)

Real transfer for canton Glarus, downloaded by the `loader` service at
container start:

`https://www.geodienste.ch/downloads/interlis/npl_waldabstandslinien/GL/ch_np_wal_v1_2.xtf`

Contains 5 real `Waldabstand_Linie` objects and 1 `Typ`. `interlis validate`
reports 0 errors, 0 warnings.

### Committed reference artifacts

- `view_waldabstand_linie.jsonfg.json` - `interlis convert-jsonfg` output
  for the `view_waldabstand_linie` VIEW only (5 Features).
- `view_waldabstand_linie.xtf` - the VIEW materialized via `interlis
  write-xtf --merge-with-source` (source baskets + the computed VIEW
  basket, one self-describing file), round-trips clean through
  `interlis validate` (0 errors).

### Simplification specific to this loader

The real transfer has exactly 1 `Typ`, shared by all 5 `Waldabstand_Linie`
via the `Typ_Geometrie` association's `WAL` role (`{1}` cardinality).
`object_to_feature` doesn't expose embedded association roles as properties
in the whole-transfer conversion mode `loader/load.py` uses (only VIEW
evaluation does, for the join it needs) - `loader/load.py` hardcodes the
single `Typ` id as the FK target for every `Waldabstand_Linie` row rather
than resolving it per-object, which is correct for this real dataset but
would need generalizing for a transfer with more than one `Typ`.

## Model 3: MainRoads_LV95_V1_1 (Projection, native 3D geometry)

### Base model

`models/MainRoads_V1_1.ili` - the real, public federal model (ASTRA),
fetched from `https://models.geo.admin.ch/ASTRA/MainRoads_V1_1.ili` (one
file declares both `MainRoads_LV03_V1_1` and `MainRoads_LV95_V1_1` as
sibling `MODEL`s - only the LV95 one is used here).

### Derived VIEW model

`models/MainRoads_LV95_V1_1_d.ili` - auto-generated by
`scripts/generate_view_corpus.py` in the main `ili2ogc` repo (federal
corpus, no `--wfs-fixtures`), already verified end-to-end
(`docs/verified-view-corpus.md`).

Like model 1's Projection, `view_roadsegment`'s `ATTRIBUTE` block doesn't
map `RoadSegment.Geometry` - but unlike model 1,
`GeometryCHLV95_V1.LineWithAltitude` is a **native** `LineType` (`POLYLINE
... VERTEX Coord3`, 3D), not a `STRUCTURE`-wrapped multi-geometry -
`convert-sql`'s `CREATE TABLE roadsegment` already carries a real
`geometry(LineStringZ, 2056)` column directly, no child table needed at
all. `pygeoapi`'s `mainroads` collection points straight at that table -
no convenience view required for this one (simpler than both model 1 and
model 2).

### Committed reference artifacts

## Model 4: BuildingLinesForMotorways_V2_2 (Projection, curved geometry)

### Base model

`models/BuildingLinesForMotorways_V2_2.ili` - the real, public federal
model (ASTRA), fetched from `https://models.geo.admin.ch/ASTRA/
BuildingLinesForMotorways_V2_2.ili`.

### Derived VIEW model

`models/BuildingLinesForMotorways_V2_2_d.ili` - auto-generated by
`scripts/generate_view_corpus.py` (federal path) in the main `ili2ogc`
repo, `ili2c`-validated. `BuildingLine.Geometry` is `GeometryCHLV95_V1.
Line` (`POLYLINE WITH (STRAIGHTS, ARCS)`) - the first model in this demo
whose real data actually contains `ARC` segments (`docs/
verified-view-corpus.md` in the main repo: "1er cas réel avec segment
ARC"), so `convert-jsonfg` produces `CircularString`/`CompoundCurve`
`"place"` values, not just `LineString`, and the collection's
`conformsTo` includes the `circular-arcs` JSON-FG conformance class.

### Source `.xtf` - a curated sample, not downloaded at runtime

Real Swiss-wide data: `https://data.geo.admin.ch/
ch.astra.baulinien-nationalstrassen/data.zip` - 3686 real `BuildingLine`
objects, ~9.5 MB zipped, ~50 MB once merged with `write-xtf
--merge-with-source`. Too large for this repo, so
`data/buildingline_sample_source.xtf` is a **30-object sample** (15 with
a plain `LineString` geometry, 15 with at least one `ARC` segment),
extracted with the runtime's own `parse_xtf`/`render_xtf` (kept every
`BuildingLine_BuildingRestrictionArea`/`BuildingRestrictionArea` object
those 30 `BuildingLine`s actually reference, not just the lines
themselves) - committed directly rather than downloaded at container
start, unlike the other 3 models. `interlis validate` reports 0 errors
against the real source's own schema (4/4 header models).

### Committed reference artifacts

- `buildingline_sample_source.xtf` - the 30-object sample itself (see
  above) - `loader/load.py` reads it directly, no download step for this
  model.
- `view_buildingline.jsonfg.json` - `interlis convert-jsonfg` output for
  the `view_buildingline` VIEW only (30 Features).
- `view_buildingline.xtf` - the VIEW materialized via `interlis
  write-xtf --merge-with-source`, round-trips clean through `interlis
  validate` (0 errors, 5/5 header models).

### Real findings this model surfaced

- **`convert-sql` types the geometry column too narrowly for ARCs**:
  `CREATE TABLE buildingline` declares `geometry(LineString, 2056)` (the
  attribute's base VERTEX type), which PostGIS rejects for a
  `CircularString`/`CompoundCurve` row - confirmed with a real throwaway
  container (`ERROR: Geometry type (CompoundCurve) does not match
  column type (LineString)`). Not an `ili2ogc` bug: the column type
  reflects the attribute's declared INTERLIS type, which doesn't
  distinguish "may have ARCs" at that granularity. This loader works
  around it with `ALTER TABLE buildingline ALTER COLUMN geometry TYPE
  geometry(Geometry, 2056)` (a generic, untyped PostGIS geometry column)
  after applying the generated schema - see `loader/load.py`.
- **`ST_GeomFromGeoJSON` can't take JSON-FG's `CircularString`/
  `CompoundCurve`** (not part of GeoJSON/RFC 7946) - this loader builds
  WKT directly from `"place"` instead (`_place_to_wkt`,
  `loader/load.py`) and loads via `ST_GeomFromText`.
- **GeoJSON itself has no curve types** - `ST_AsGeoJSON` on a
  `CompoundCurve`/`CircularString` value errors outright (confirmed:
  `lwgeom_to_geojson: 'CompoundCurve' geometry type not supported`).
  Since `pygeoapi` (core GeoJSON serving AND the JSON-FG formatter, which
  wraps pygeoapi's own GeoJSON) needs this to succeed, `pygeoapi`'s
  `buildinglines` collection is served through a convenience view
  wrapping the geometry in `ST_CurveToLine(...)`
  (`loader/post_load_buildinglinesformotorways.sql`) - the live map
  shows a linearized approximation of any curved `BuildingLine`; the
  true curve survives in PostGIS's own `buildingline.geometry` column
  and in `data/view_buildingline.jsonfg.json`. This is an inherent
  GeoJSON limitation, not a bug in any of the 3 "judges" this demo
  compares.
